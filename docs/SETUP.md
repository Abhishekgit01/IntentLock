# Development setup skeleton

The repository currently has no application or contract scaffold. This document defines the setup and toolchain pinning policy as code lands; it deliberately distinguishes selected pins from values that must be generated by a real clean install. Do not run install commands against unreviewed floating dependencies and then call that a reproducible build.

## 2. Foundry reproducible installation & verification

Foundry must be installed and pinned reproducibly across contributor environments:

### Installation commands

**Linux / macOS / WSL:**
```sh
curl -L https://foundry.paradigm.xyz | bash
foundryup
```

**Windows (PowerShell):**
```powershell
irm https://raw.githubusercontent.com/foundry-rs/foundry/master/foundryup/install.ps1 | iex
foundryup
```

### Verification commands

```sh
forge --version
anvil --version
cast --version
```

*Status:* **Pending local toolchain install & contract scaffold** in this workspace. Local environment probe confirmed `forge` is not on the system PATH. Once installed and once the contract scaffold is created, record the exact commit/release hash output from `forge --version`.

## 3. Required runtime configuration

Keep local-only values in an ignored `.env.local`; commit only `.env.example` with empty/non-secret placeholders. Validate all values at startup.

```dotenv
CHAIN_ID=31337
RPC_URL=http://127.0.0.1:8545
SAFE_ADDRESS=
SAFE_VERSION=1.4.1
GUARD_ADDRESS=
REGISTRY_ADDRESS=
TIMELOCK_ADDRESS=
VERIFIER_SET_ID=
POLICY_HASH=
DEMO_SCENARIO=baseline
```

These are placeholders, not deployable addresses or secrets. Never put verifier private keys in this file if it is loaded by the browser. Verifier keys stay in a local verifier process and use disposable Anvil accounts only.

## 5. Expected scripts as implementation lands

Add deterministic scripts with these responsibilities:

- `anvil`: start local chain with the expected chain ID and disposable accounts.
- `deploy`: deploy pinned Safe, vault fixtures, registry, guard, and timelock; assert configuration and write deployment manifest.
- `reset-demo`: restart from genesis, deploy, configure, fund, install guard, assert no modules, and run smoke scenarios.
- `test`: run `forge test` and report stable fixture IDs.
- `report`: read machine-readable results and generate metrics from the catalog without altering expected outcomes (`scripts/report_fixtures.py`).
- `dev`: start the UI/API adapter only after health checks pass.

Every script must stop on the first failed health assertion. The deployment manifest should include Safe tag/commit, compiler and optimizer settings, chain ID, contract addresses/code hashes, verifier set and threshold, policy hash, timelock delay, and initial fixture state.

## 6. Clean-checkout acceptance

Setup is complete when a teammate can follow committed instructions from a clean checkout, install only pinned dependencies, start Anvil, deploy/reset, execute the valid and rejected fixtures, run `forge test`, and regenerate the report. Until then, this file is a setup record tracking verified facts and clearly labeling pending steps.
